# 登录验证码不变量

| 编号 | 不变量 | 保持机制 |
|---|---|---|
| AUTH-OTP-1 | 挑战只绑定一个活动店铺（ACTIVE shop + ACTIVE merchant） | 插入事务内按 shopCode 锁定店铺行 |
| AUTH-OTP-2 | 明文验证码不入库、不出现在 HTTP 响应 | 只存散列；API 只回 `challengeId`/`ttlSeconds`/`expiresAt`/`resendAfterSeconds`/`nextSendAt` |
| AUTH-OTP-3 | `Dispatch` 不在业务事务内 | usecase 先提交再调 `Notifier` |
| AUTH-OTP-4 | 请求渠道非 `SENT` 时对用户返回发送失败，挑战仍保留；另一渠道 `SENT` 不能顶替 | 解读 Platform deliveries 中与请求 `channel` 相同的项；不回滚插入 |
| AUTH-OTP-5 | 调用方模块前缀必须等于 eventKey 前缀；Identity 只 Dispatch 自己的事件 | 客户端写死 `identity.auth.otp.requested` |
| AUTH-OTP-6 | 同店同目的地新挑战使旧 `PENDING` 过期 | 插入前条件更新 |
| AUTH-OTP-7 | `CONSUMED` 挑战只能被 `/auth/login` 兑现一次，且必须在 `consumed_at` 后 300 秒内 | `login_session_id` 唯一；超时或已兑现失败关闭 |
| AUTH-OTP-8 | 游客升级不得只改写 principal type；同店无既有顾客时把当前 `GUEST` 主体升为 `CUSTOMER` 并写入凭据，已有同店凭据则签发到该顾客并撤销游客会话 | 同一登录事务；跨模块购物车等通过 `identity.guest.upgraded` Outbox 通知，本事务不写 Catalog |
| AUTH-OTP-9 | 同店同目的地在 60 秒冷却内不得再创建挑战，也不 Dispatch；按钮倒计时由服务端 `resendAfterSeconds`/`nextSendAt` 给出 | `CreatePending` 按最近 `created_at` 拒绝并返回剩余秒数 |
