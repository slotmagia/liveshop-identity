# 事务与失败窗口

## 套餐目录写入

套餐 guard 行锁、幂等命令插入、expected version 校验、套餐主行写入、默认套餐切换和 canonical response 落账在同一 MySQL 事务完成。新建套餐还在该事务初始化空权限集合和显式不限额额度行，但创建请求不能指定权限或额度。

- 请求在提交前失败：套餐基本信息、默认标记、初始策略行和命令账本全部回滚。
- 提交成功但响应丢失：调用方用同一 `command_key` 和载荷重试，读取首次 canonical response，不重复递增 version。
- 同键异载荷：拒绝，不覆盖首次命令。
- 不同命令并发修改同一套餐：guard 与 expected version 使其中一项成功，另一项冲突。
- 切换默认套餐：清除旧默认和设置新默认处于同一事务；任意一步失败都保留原默认。
- 退役：只把状态推进到 `RETIRED`，不删除历史套餐、权限或额度模板；退役默认套餐被拒绝。

## 套餐权限策略写入

策略命令账本插入、套餐行锁、expected policy revision 校验、活动 Registry 权限校验、权限全量替换、`catalog.products` 额度写入、policy revision 递增和 canonical response 落账在同一 MySQL 事务完成。

- 请求在提交前失败：权限、额度、revision 和策略命令账本全部回滚。
- 响应丢失：同 command key、同载荷读取首次 canonical response；同键异载荷冲突。
- 两个管理员并发配置同一套餐：只有 expected policy revision 匹配者成功，另一请求重新读取后再编辑。
- Registry 权限在策略事务后失活：历史码仍可审计；下次保存必须从活动目录重新选择。商户权益应用前还要再次校验活动权限。
- 套餐已退役：策略读取和写入均拒绝，历史权限与额度行不删除。

## 套餐额度写入

`subscription_quota_command` 插入、当前 entitlement 行锁、expected revision 校验、entitlement 写入和 command 结果写入在同一 MySQL 事务中完成。

- command 成功而 entitlement 失败：事务整体回滚，稳定 key 可重试。
- 响应丢失：同 key、同载荷读取已提交 revision 并返回 replay。
- 同 key、异载荷：拒绝，不覆盖原事实。
- 不同 key 并发更新同一额度：只有 expected revision 匹配者成功，另一请求冲突后重新读取。

## Catalog 建品

Subscription 的只读调用不能与 Catalog 数据库形成分布式事务，因此额度上限先按 deadline 查询。Catalog 随后在自己的事务中锁定 app 级额度闸、统计其拥有的商品事实，并原子校验及写入。Subscription 不提供预占，是为了避免预占成功而 Catalog 回滚、租约回收、重复消费及双事实源问题。

套餐在查询后被收窄是一个跨服务窗口。调用方必须保存本次使用的 entitlement revision 到建品/导入审计事件，并由套餐变更流程禁止把新上限直接收窄到低于现有使用量；这一管理端不变量需要完整 Subscription 套餐迁移继续实现，不能由 Catalog 静默删除既有商品补偿。

## 权限权益写入与 Identity 投影

`subscription_permission_entitlement_command`、当前态行锁、expected revision、全量 item 替换和 canonical response JSON 在同一事务提交。响应丢失后旧命令仍返回首次结果；它不会回滚后来已提交的 revision。数据库任一步失败则命令账本和事实同时回滚。

Identity 使用 mTLS 周期读取完整快照。Identity 在自己的事务中比较 `(revision,digest)`：新 revision 原子替换 items 并更新授权域；同 revision 同摘要只刷新 `projected_at`；乱序或同 revision 异摘要拒绝。跨库失败窗口只会留下旧投影，超过 `max_staleness` 后 readiness、有效授权和 Module Capability 全部失败关闭，后续同步重试收敛。

## 商户购买订单

`subscription_order_command` 插入、在途单复用或新建、套餐 `ACTIVE` 与价格快照在同一 MySQL 事务完成。支付发起是随后对 Trade 的同步调用，不进入该事务。

- 下单在提交前失败：订单和命令账本全部回滚。
- 下单成功但 Trade 收款不可用：订单保持 `PENDING` 或请求在调用 Trade 前失败关闭；不得把未收款订单标为 `PAID`。
- 开通：锁 `PENDING` 订单、标 `PAID`、按快照计算到期并写入 `subscription_merchant_assignment` 在同一事务。随后同库应用权限/额度 entitlement（与总后台指派相同的后续步骤）。
- 并发开通同一订单：只有一次 `PENDING → PAID` 生效，其余读取已开通结果。
- 同档续费：若当前指派未过期且套餐码相同，到期日从当前到期顺延；否则从当前时间起算。

## 关闭未支付订单

`subscription_order_command` 插入、锁订单、`PENDING → CANCELLED` 和 canonical response 在同一 MySQL 事务完成。`pending_slot` 是 generated column，状态离开 `PENDING` 后自动变为 `NULL`，不需要额外 UPDATE。

- 请求在提交前失败：状态和命令账本全部回滚。
- 已 `CANCELLED`：同键同载荷重放首次结果。
- 非 `PENDING`：冲突，不改状态。
- Identity 不调用 Trade 取消支付单。

## 旧 Platform 单次交接

Platform 先冻结一个 canonical 全量 envelope。Identity importer 校验整个 envelope，只导入角色、grant 和 scope；Subscription importer 校验同一 envelope，只导入 `platform_entitlement_projection`，并记录 `exportRowCount`、`targetImportedRowCount` 和 `targetProjectionDigest`。两边各自同事务保存事实和不可变 ledger，再签发精确绑定 export digest/import ID/target 的 receipt。Platform 持久化两份有效 receipt 后才删除旧表；任何一份缺失、冲突或签名失败都不删除。
