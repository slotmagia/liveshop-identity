## L0 原则与开工

1. 从当前目录向上读取所有 `AGENTS.md`。
2. 读 `docs/domain/` 五件套：`事实.md`、`不变量.md`、`状态机.md`、`事务.md`、`外部契约.md`。它们是本模块业务事实的唯一来源。
3. 先跑 `./business/backend/tools/verify-domain.ps1`。失败说明还没人做业务决策，**不要开始实现**。
4. 关键事实、不变量或状态机没有业务依据时，停止实现并提出最小澄清问题。

### L0.1 领域语义保持

从旧项目迁移时，目标是用当前架构重构实现，同时保持旧源码、数据库约束、接口、状态机和可观察行为共同证明的业务语义。

- 模块按业务能力命名；`admin`、`merch`、`shop`、`live` 只是交付 surface。
- 开工前在 `事实.md` 列出旧表/字段、唯一键、状态、关系、授权规则和目标承载位置。无法从证据确认时停止实现。
- 店铺隔离是 `merchant_id + shop_id`。不要生成 `app_id`/`commercial_id` 运行时列。`shop_id` 不得映射为组织/部门 ID。
- 公共身份或 Module Capability 缺少店铺范围时，演进 Kernel、Identity、Gateway 和调用方；需要权限定义时同步演进 Platform Registry。禁止把值塞进 `departmentIds` 或未验证 header。
- 可以替换不安全实现，但必须保留多店铺、角色与数据范围、状态机、会话、幂等结果。
- 有意改变旧行为必须独立记录业务决策和数据迁移，不能夹带在模块拆分中。

迁移验收必须对照旧场景：身份、隔离维度、状态、最终数据和副作用，而不只是状态码。

### L0.2 四端组织与身份硬约束

四端硬约束如下。

- `admin`、`merch`、`shop`、`live` 是 surface，不是四套 Identity、Realm 或组织树。
- 只建立平台组织和商户组织。店铺是商户业务范围；主播是固定店铺的岗位主体。
- `subject` 全局稳定，租户范围通过成员关系表达；平台主体不得伪造 `merchant_id`。
- 商户以全局 `merchant_id` 为主键，店铺以 `shop_id` 为主键并归属一个 `merchant_id`。claims 只携带 `merchantId + shopId`。
- `MERCHANT_OWNER` 派生本商户全部有效店铺；`MERCHANT_STAFF` 可有多个 `OPERATE` 店铺；`SHOP_ANCHOR` 只有一个 `ANCHOR` 店铺且同店最多一个有效主播。
- Identity 拥有主体、凭证、Access Identity、会话、商户、店铺、组织、成员关系，以及角色、策略、Subject grant、数据范围和有效授权；Platform 只拥有 Registry 权限定义、活动 Manifest、Settings 与 Audit。
- 员工创建、组织/店铺范围与角色授予由 Identity 在同一事务命令中完成；Subscription capability 拥有商户 permission entitlement SOT，并在同库内按 revision/digest 原子刷新授权读模型。缺失、冲突或过期均失败关闭。

## L1 工程目录

```text
identity/
├─ go.work
└─ business/
   ├─ module.json
   ├─ backend/
   │  ├─ cmd/archcheck/
   │  ├─ configs/
   │  ├─ docs/                    # 本手册 + domain 五件套
   │  ├─ migrations/
   │  ├─ tools/
   │  └─ internal/identity/
   ├─ frontend-admin/             # iframe
   ├─ frontend-merch/
   ├─ frontend-shop/              # remote ESM
   └─ frontend-live/
```

Identity 线协议在兄弟仓 `liveshop-protocol/identity/`。`business` 依赖该子目录；反向禁止。不把其他模块 Proto 拷进来。

```text
backend/internal/identity/
├─ config/                        # schema + 启动校验
├─ app/                           # dependencies / surfaces / bootstrap / run
├─ capability/<name>/             # 内部能力：model、usecase、仓储端口
├─ biz/                           # 仅跨 capability 模块级用例
├─ data/<name>/                   # mysql 生产适配；memory 仅测试
├─ application/<surface>/
│  ├─ api/http/v1/<domain>/
│  ├─ appmodel/
│  ├─ service/
│  ├─ logic/
│  ├─ controller/http/
│  └─ router/http.go
├─ worker/
├─ common/                        # authctx、middleware、web、server
└─ cmd/
```

capability 子目录不是微服务：禁止自建 `go.mod`、`module.json`、独立库连接或进程入口。

## L2 功能边界

权威：`internal/identity/capability/README.md`。所有 capability 共用本模块进程、数据库、Manifest 和发布生命周期。

| Capability | 拥有 | 不拥有 |
|---|---|---|
| `auth` | 认证、凭据、会话、验证码挑战/核验、上下文切换 | 短信/邮件投递证据（Platform notification） |
| `subject` | 全局主体、realm、旧身份映射 | 商户经营关系 |
| `merchant` | 商户主体与经营关系 | 店铺实体 |
| `shop` | 店铺、商业隔离映射、结算币种、店铺自定义域名绑定与 TXT 验证 | 组织部门树、公网根域名/证书（Platform） |
| `workforce` | 平台操作员、商户员工、主播、组织/店铺范围 | 角色策略定义（在 authorization） |
| `authorization` | 角色、策略、grant、数据范围、有效授权 | Registry 权限码定义（Platform） |
| `subscription` | 套餐、配额、商户权限权益、revision、命令账本 | 支付扣费（Trade） |
| `customer` | 客户档案、地址、标签、备注、收藏 | 订单（Trade） |
| `fulfillment` | 配送规则、物流、售后、投诉 | 支付退款（Trade） |
| `risk` | 游客风险事件、状态、版本化决策 | 原始埋点（Platform telemetry） |
| `customer_service` | 外部/直播客服账号、渠道分配 | 直播房间（Live） |
| `merchant_governance` | 商户能力摘要、设置治理、幂等干预 | Platform Settings 本体 |

跨 capability 写入必须由模块级用例明确事务边界；任何 capability 不得直接修改另一个 capability 的表。禁止导入其他模块 `internal`、DAO 或数据库。

## L3 后端

### L3.1 分层

依赖方向：`application/<surface>` → `capability/<name>` / 模块级 `biz` → 仓储端口 ← `data/<name>`。

| 层 | 唯一职责 | 禁止 |
|---|---|---|
| `capability/*/model`、`biz/model` | 事实、不变量、状态机、领域错误 | GoFrame、SQL、HTTP DTO |
| `capability` usecase / `biz` | 用例与仓储端口 | `application`、驱动、Req/Res |
| `data` | SQL、事务、锁、行映射 | HTTP DTO、`application` |
| `api/http` | g.Meta、XxxReq/XxxRes | `biz`、`data`、其他 surface |
| `appmodel` | 传输中立出入参 | `Req`/`Res` 后缀 |
| `service` | 边界接口 | 实现、传输 DTO |
| `logic` | claims → 用例 | GoFrame、SQL、跨 surface |
| `controller` | DTO ↔ appmodel | SQL、biz 直调、权限判断 |
| `router` | 分组、中间件、Bind | 业务规则 |
| `common/middleware` | **唯一**把凭证变成上下文 | 业务规则 |
| `app` | 装配与生命周期 | 业务规则、读环境变量 |

`application/` 只允许 `admin`、`merch`、`shop`、`live`，且必须与 `frontend-<surface>` 和 Manifest contribution 一一对应。**surface 之间禁止相互导入。**

### L3.2 通用初始化

```text
cmd → -config 唯一 YAML → config.Validate
    → gfinit.MustInit
    → app/dependencies.go 显式构造 DB、签发器、仓储
    → app/surfaces.go 装配各 surface
    → common/server 唯一 HTTP 组合根
    → app/run.go 生命周期
```

禁止环境变量覆盖、隐式 overlay、`init()` 注册全局单例。缺配置必须启动失败。Identity 是 Module Capability 的**唯一签发方**；其他模块只构造 Verifier。

### L3.3 编码

- HTTP 用 GoFrame；`g.Meta` 的 path+method 与 `module.json` 逐字相同。
- 跨模块同步用对方 protocol 的 gRPC；异步用本模块 Outbox。
- 写命令：稳定幂等键 + 预期版本；物理删除改为终态。
- JSON camelCase；表名 `identity_<aggregate>`；migration 只追加。
- 领域错误 `model.Err*`；HTTP 状态只由 `common/web` 映射。
- 格式门禁用 `gofmt -l`。

### L3.4 新增能力顺序

```text
1. domain 五件套 + capability README
2. module.json operation / 权限 / contribution
3. capability model → usecase/port → data 事务适配
4. 跨 capability 才进入模块级 biz
5. application/<surface>：api → appmodel → service → logic → controller → router
6. app 显式注入
7. 前端 artifact 与 allowedRoutes
8. verify-domain + verify-fast + 鉴权样板测试
```

## L4 前端与 UI

admin/merch 为 iframe，shop/live 为 remote ESM。凭证只来自 `connectToHost()` 或 `mount` 的 context。用 `@liveshops/host-sdk` 发请求，禁止手写 Gateway 地址和 Authorization 头。

后台必须遵守本仓库 [`docs/开发规范.md`](../../../docs/开发规范.md) 第 5 章：

- 结构：Host 说明卡 + `searchCard()` + `dataCard()`，三者左右对齐。
- 查询：`searchForm()` 自动搜索；分页不进查询表；`kind: 'select'` 点选即选中。菜单 portal 到当前文档 `body`，`--ls-z-popover` 必须高于 Host 表单模态遮罩。
- 弹窗：普通表单用 `hostFormModal()`（参照用户管理页）；禁止自建 backdrop、HTML5 fullscreen、改父 DOM。
- 权限多选用 `checkbox-tree`。
- 组件与色号只来自 `@liveshops/design-tokens`；禁止 `var(--ls-x, #fallback)` 和静态 `innerHTML`。

`package.json.name` = `@liveshop/identity-<surface>`，版本与 `module.json` 一致。

## L5 命名与 Manifest

权威：本仓库 [`docs/开发规范.md`](../../../docs/开发规范.md) 第 6 章。检查入口：[命名规范检查.md](../../../docs/命名规范检查.md)。**新增接口按第 6 章写；已发布 id 不在本手册改名。**

```text
id   = identity.<surface>.<domain>.<feature?>.<method>
path = /<surface>/identity/<domain>/...
权限 = identity.<resource>.<action>          # 不含 surface
贡献 = identity.<surface>.<page>
占位 = identity.placeholder.<surface>.<page>
```

正例：`identity.admin.subscription.plans.retire` → `POST /admin/identity/subscription/plans/{planId}/retire`  
本模块注册 domain 以本仓库 [`docs/命名规范检查.md`](../../../docs/命名规范检查.md) 与 [`docs/开发规范.md`](../../../docs/开发规范.md) 第 6.3 节为准，例如 `customer-accounts`、`merchant-governance`，不要用 `customer-service` / `settings-governance`。

| 对象 | 规则 | 示例 |
|---|---|---|
| api 包 | `api/http/v1/<domain>/`，类型 `XxxReq`/`XxxRes` | `api/http/v1/users/ListReq` |
| appmodel | 名词，不带 `Req`/`Res` | `appmodel.UserPage` |
| service 方法 | 动词开头，只用 appmodel | `ListUsers(ctx, appmodel.UserQuery)` |
| 表 | `identity_<聚合>` | `identity_subject` |
| migration | `NNN_<描述>.sql`，只追加 | `014_add_shop_currency.sql` |
| Proto | `identity.v1`，服务 `<聚合>Service` | `identity.v1.SubjectService` |
| 领域错误 | `Err<条件>` | `model.ErrSubjectNotFound` |

权限码一旦发布就是契约。改名等于删旧建新。角色与授予事实只在 Identity 写入。

## L6 接入与引用

```text
module.json ──注册──> Platform Registry ──路由快照──> Gateway ──Identity Module Capability──> 本模块
                                      └─活动能力快照──> Identity runtime
```

1. 把 `business/module.json` 提交到 Platform registry 并激活。
2. `origin` 必须是 Gateway 能访问的地址。
3. `module_capability.private_key` 是唯一签发私钥（base64url 无填充）；Gateway、Platform 与业务模块只配对应公钥。能力有效期不得超过 5 分钟。
4. 加 `frontend-<surface>` 时必须同时补 contribution，`allowedRoutes` 覆盖该 surface 实际路由。

排查：401 看 token；403 先看 `X-Liveshop-Surface`，再看 `allowedRoutes`，最后看权限码；404 回到注册。

允许依赖：`kernel-go`、本模块 protocol、他模块 **已发布** protocol、npm 已发布的 `@liveshops/host-sdk@0.3.4` 与 `@liveshops/design-tokens@1.5.3`（禁止 `file:` 指向 Platform 源码）。禁止导入他模块 `internal`。

## L7 硬性约束、门禁与完成

### 硬性约束

- **清单即契约**：`authentication` 与 `requiredPermissions` 必须在 router 挂中间件真正执行。
- **鉴权**：只有 `common/middleware` 能把凭证变成上下文。每个能力挂自己的 `RequirePermission`。
- **配置**：只读 `-config` 指定的一份完整 YAML。
- **错误**：`logic` 返回领域错误；HTTP 由 `common/web` 映射；gRPC 状态码禁止从 HTTP 推导。未识别错误降级为通用失败，真实原因写日志。
- **装配**：显式注入，禁止全局访问器和 `init()` 注册。
- **写入**：校验预期旧状态或版本；可重试命令有稳定幂等键。
- **一致性**：跨存储用 Outbox/Inbox，不要事务后“尽力发布”。
- **存储**：生产用真实事务库；`data/memory` 只服务单元测试。
- **迁移**：只追加。

### 门禁

`cmd/archcheck` 按传递闭包强制依赖方向。提交前：

```powershell
./business/backend/tools/verify-fast.ps1
```

改了 SQL/事务/鉴权/并发：跑真实数据库集成测试。改了 Manifest/Proto/migration：跑发布级校验。

### 测试

样板：`internal/identity/app/server_test.go`。覆盖放行、无凭证、缺权限、路由越权、surface 头不符。每个能力至少一条放行和一条拒绝。一致性流程还要断言库内最终状态、版本、事件次数和重复执行副作用。

### 常见错误

| 错误 | 正确做法 |
|---|---|
| controller 调 biz 或读库 | 只做 DTO ↔ appmodel，经 service |
| service 出现 XxxReq/XxxRes | 只用 appmodel |
| 规则在内存与 SQL 各写一遍 | 只写在 capability/biz model |
| 环境变量临时开关 | 写入配置 schema 或放弃 |
| 跨 surface 复用 api DTO | 各写一份 |
| 清单声明权限但 router 没挂 | 两边同时改 |
| 只用 go fmt 当门禁 | 用 `gofmt -l` |
| TODO(domain) 就开始写代码 | 先跑 verify-domain |

### 完成的定义

- [ ] `verify-domain.ps1` 通过
- [ ] `verify-fast.ps1` 在干净树上第一次通过
- [ ] 新 operation 的 id/path 符合 24；权限码与 router 一致
- [ ] 有放行用例和拒绝用例
- [ ] 一致性写入有幂等与副作用断言
- [ ] 改 SQL 的跑过真实库集成测试
- [ ] Proto/migration 只追加；生成脚本已跑
- [ ] 后台页遵守 23；交付说明含可复现命令

「完成」= 故障后不变量仍收敛，不是接口返回 200。
